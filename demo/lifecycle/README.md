# Head lifecycle under different scenarios

This scenario shares the benchmark's devnet, valid transaction datasets, node
startup, funding, deposits, close and fanout. It is driven by protocol events;
the configurable holds give a person time to see each state on Grafana.

The first scenario opens and funds a three-party Head, confirms baseline
transactions, suspends one Hydra process and its etcd child, proves a submitted
transaction remains unconfirmed during the outage, resumes the participant,
checks confirmation on all three participants, sends further transactions,
closes, and fans out.

The node and its etcd child are suspended, so the peer stops serving both Hydra
and etcd requests. Two of three etcd members remain available for quorum. This
is a missing-signer/leader scenario. Depending on the next leader, a snapshot
can wait to start or wait for its last signature. The scenario checks that both
remaining participants receive the transaction, that confirmation stops, and
that it then recovers. Suspension is bracketed:
exceptions and cancellation resume both processes before cleanup. Suspension
models an unavailable peer; it does not exercise process exit or restart.

## Run the scenario

From the repository root:

```sh
nix develop .#hydra-cluster-bench --command bench-e2e lifecycle \
  --output-directory /tmp/head-lifecycle \
  --seed 42 --number-of-txs 12 \
  --phase-seconds 10 --peer-pause-seconds 20 --tx-interval-ms 250
```

Use a fresh output directory. This always starts a local devnet; no public
network or existing node is controlled. `--number-of-txs` is the length of the
single transaction chain submitted by the scenario; all participants observe
that same chain. Two other datasets supply initial Head funds.

For a shorter rehearsal, use three transactions, zero phase holds and a
one-second peer pause. `--timeout 600s` bounds the run. The seed fixes dataset
generation, not scheduling, keys generated by the devnet, or elapsed times.

## Metrics showcase

Add `--metrics-showcase` to run the extended local scenario:

```sh
nix develop .#head-lifecycle-demo --command \
  python3 demo/lifecycle/run.py --metrics-showcase \
  --output-directory /tmp/hydra-metrics-showcase \
  --number-of-txs 24 --phase-seconds 8 --peer-pause-seconds 20
```

The recorder follows the metric chapters in `showcase.json`, using panels from
the checkout's dashboard. It focuses on the first participant to keep series
readable, while the reachability panels continue counting all participants.
Each chapter uses a one-minute window and refreshes every two seconds. Captions remain editable in
`video/captions.srt`; the raw browser recording has no embedded caption overlay.

After the baseline traffic and missing-signer fault, the extended scenario:

- Submits an unsigned transaction and an out-of-order dependent transaction,
  requiring invalidation after the latter's retry window.
- Deposits additional funds and waits for their on-chain finalization.
- Suspends the owned Cardano devnet while a decommit waits in an L1 operation,
  then queues further inputs behind it. The monitoring endpoint must remain responsive.
- Resumes Cardano and requires the decommit to finalize and the queue to drain.
- Suspends two owned etcd services while keeping Hydra and monitoring running,
  then sends duplicate submissions until the broadcast hand-off stalls. A new
  client transaction must be refused explicitly. After restoring quorum, the
  queued transaction must confirm on every participant and the stall must clear.
- Closes the Head, distributes one selected output, leaves the rest visibly
  deferred, then explicitly selects the remainder and requires finalization.

All process suspensions are scoped and resume on failure or cancellation. The
scenario waits on actual metric values before reporting queue and stall states;
it saves Prometheus samples in `scenario/evidence/`. Duplicate submissions are
deliberate workload, not distinct transactions. The scenario does not exercise
Blockfrost, deep chain rollback or transaction timer-cache eviction. Fast SQLite
write and queue gauges can remain zero between scrapes even when batch-latency
histograms record completed work.

For an edited film, `render.py` reads a JSON script with a recording path and a
list of excerpts, each containing `start`, `end` and `caption`. Times are seconds
in the original recording. An optional `speed` changes playback speed; identify
slowed or accelerated excerpts in their captions. It produces one MP4, an editable SRT, a Markdown
transcript and an uncaptioned edit:

```sh
nix develop .#dashboard-recording --command \
  python3 demo/lifecycle/render.py --edit /tmp/film-script.json \
  --output-directory /tmp/finished-film
```

The JSON script is the source of caption wording and edit timings; changing it
and rerunning the renderer updates the video and transcript together. The raw
timeline and camera changes in `video/capture.json` provide the timing evidence
for the script. Raw event captions use wall-clock offsets. The encoded browser
video can drift from that clock, so align edited excerpts against their recorded
frames. Timestamped milestone screenshots provide anchors for that alignment.

The output directory retains:

- `dataset.json`: the generated workload.
- `timeline.jsonl`: timestamped phase events, flushed as they occur, including
  failure events. `applied` distinguishes an intervention from an `observed`
  protocol result.
- `targets.json`: Prometheus file discovery targets using allocated ports.
- `endpoints.json`: node IDs, API endpoints and monitoring ports.
- Node, chain and test logs and local persistence for diagnosing a failed run.

Failures are fatal: a confirmed transaction during suspension, missing recovery
confirmation or failed fanout cannot become a successful scenario report.

## Record the dashboard

The Linux recording shell supplies the benchmark, node binaries, Prometheus,
Grafana, Python/Playwright, its matching browsers and FFmpeg:

```sh
nix develop .#head-lifecycle-demo --command \
  python3 demo/lifecycle/run.py --output-directory /tmp/head-lifecycle-recording --mp4
```

This starts monitoring on loopback ports 9090/3000, provisions a copy of the
checkout's dashboard, records a 1920×1080 browser viewport, then runs the
scenario. Ports can be changed with `--prometheus-port` and `--grafana-port`.
The dashboard copy resolves its datasource UID and instance filtering to the
scenario's allocated ports. Repository dashboards and production alert timings
are not modified. Prometheus scrapes every two seconds; Grafana refreshes every
five seconds.

Use `--dashboard PATH` to provision a different dashboard JSON. For a video
whose captions will be edited after recording, use `--no-overlay`; the timeline
and editable `captions.srt` are still saved alongside the recording.

The runner creates a private local Grafana password for writing dashboard
annotations. Viewing is anonymous and read-only. The recorder adds annotations
and on-screen captions from the actual scenario timeline. `GRAFANA_TOKEN` can
instead authorize annotations when using an existing Grafana instance.

The recording contains `video/recording.webm`, optional `recording.mp4`,
`captions.srt`, screenshots at observed milestones, `events.json`, capture
metadata and the scenario's combined stdout/stderr. Monitoring state and logs
are retained beside `scenario/`. A failed scenario produces a failed command
and preserves the recording; it is never silently reported as a successful demo.
Capture can be interrupted: the recorder first interrupts the scenario so its
process brackets can unwind, with a bounded process-group kill as a backstop.

For an existing Grafana instance, use `record.py --help`. Pass login state with
`--storage-state` if needed, a dashboard readiness selector, a fresh timeline
path, a fresh video directory and the scenario command after `--`. This mode
does not start or reconfigure monitoring.

Run recording unit tests without browser dependencies:

```sh
python3 demo/lifecycle/test_record.py
```

Exercise browser capture, MP4 encoding and failure preservation as well:

```sh
nix develop .#dashboard-recording --command \
  env HYDRA_RECORD_BROWSER_TESTS=1 python3 demo/lifecycle/test_record.py
```

This initial slice provides a complete lifecycle, one controlled peer fault and
recording infrastructure. Calibrated open-loop bursts, loss of etcd quorum,
incremental funds workflows and phase-specific camera framing can be added as
further scenarios. It has no dependency on the metrics-audit branch: after this
work merges, rebasing that branch makes the richer dashboard available to the
same recording command.
